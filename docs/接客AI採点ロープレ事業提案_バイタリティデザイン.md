### バイタリティデザイン合同会社 向け
*作成: 2026-06-27 / ベース: wheelsUp Sales（建築転職エージェント向け面談採点AI）の実装知見*

## 0. エグゼクティブサマリー

- **仮説**: 既存の「面談採点AI（wheelsUp）」のエンジンは、現場接客の採点・育成にそのまま転用できる。
- **市場の裏付け**: IDOM・プリモGHD・フロンティア等が2025〜26年にAI接客ロープレを導入し、早期戦力化・指導負担減で成果を出している（日経 2026/6/25）。
- **結論**:
  - **接客の「実データ採点」は、既存エンジンの業界差し替えでほぼ実現可能（フェーズ1・短期）。**
  - **AIが客役の「リアルタイムロープレ」は新規アーキテクチャが必要（フェーズ2・中期）。**
- **推奨**: フェーズ1（接客採点PoC）を別アプリとして小さく立ち上げ、市場の追い風を捉える。

## 2. 既存システム（wheelsUp）の中核構造

現行システムは「建築転職エージェントの初回面談」を採点するAIだが、その**エンジンは業界非依存の汎用構造**を持つ。

```
発話データ（議事録/文字起こし）
   ↓ ①観察抽出      … 発話から「観察可能な行動」を引用付きで抽出
   ↓ ②ルーブリック採点 … 各項目の達成条件を満たしたかで0〜10点
   ↓ ③お手本比較     … トップ人材（小林）の基準・実データと対比
   ↓ ④構造化整形     … 「01診断フォーマット」5項目に整理（必須項目の充足/欠落を可視化）
フィードバック（点数＋根拠引用＋次の一手＋お手本との差分）
```

### 接客に置き換えると（そのまま転用可能）

| wheelsUp（転職面談） | 接客版（バイタリティデザイン） |
|---|---|
| 議事録 | 接客の録音・文字起こし |
| 5軸（ニーズ/提案/信頼/前進/情報） | 接客チェックリスト（挨拶/ヒアリング/提案/クロージング/必須ワード） |
| 小林（Sランク）のお手本データ | トップ販売員の接客データ |
| 観察ファースト採点 | 行動の有無で採点（印象でなく事実） |
| 01診断「確認できず」検出 | **必須ワード・確認事項の漏れ検出** |
| leader_comparison | トップ販売員ならどう対応したかの差分 |

**特に「確認できず」検出 ＝「必須ワードが漏れていないか」**は、フロンティア社の評価項目と同型。既存実装の直接流用が効く。

## 3. 転用可能性のマッピング

### ✅ そのまま使える（フェーズ1で即活用）
- ルーブリック/チェックリスト採点エンジン
- 観察抽出＋引用照合（ハルシネーション防止：実発話に無い引用は弾く）
- お手本（トップ人材）との比較採点
- 構造化整形（必須項目の充足/欠落の可視化）
- 話者分離（接客では「スタッフ vs 客」の分離に対応）
- 軸別フィードバック＋学習教材（接客の型を学ぶ導線）

### ⚠️ 作り替え/追加が必要（フェーズ2の本命）
- **リアルタイムAI客役**（会話するロープレ相手）← 今は「終わった会話の採点」のみ
- **音声解析**（話す速さ・声色・間・抑揚）← 今はテキストのみ
- **表情解析**（IDOMが審査）← 映像処理が必要
- **チェックリストの粒度**（30項目×5段階の細かい型）← 今は5軸×0-10
- **業界テンプレート化**（建築転職にハードコード → 接客テンプレへ）

## 4. プロダクト2段階構想

### フェーズ1：接客「実データ採点」（短期・既存資産で勝てる）
**やること**: 実際の接客（録音/文字起こし）をチェックリストで採点しフィードバック

- 接客チェックリスト定義（必須ワード・接客フロー・NG行動）
- トップ販売員の接客を「お手本データ」に登録（小林ポジション）
- 録音→文字起こし→採点→フィードバック
- **既存コードの業界差し替えで最短実装**

**価値**: 全店の接客品質の見える化・標準化、店長/トレーナーの採点負担減

### フェーズ2：AI客役「リアルタイムロープレ」（中期・本命）
**やること**: AIが客として応答し、スタッフが練習。終了後に採点

- 会話するAI客（ペルソナ×シナリオ。フロンティアの30顧客像が参考）
- リアルタイム音声対話（speed/tone/間の解析）
- 終了後に30項目チェックリストで5段階採点
- **新規アーキテクチャ**（ストリーミングLLM＋音声＋リアルタイム採点）

**価値**: 指導者不在でも反復練習、緊張せず壁打ち、早期戦力化

## 5. 技術アーキテクチャの注意点（実装知見）

現行 wheelsUp 開発で得た重要な教訓:

1. **Vercel Serverless（60秒制限）はロープレ（フェーズ2）には不向き**
   - バッチ採点・整形ですらタイムアウトが頻発した
   - リアルタイム音声対話には別基盤（常駐サーバ/エッジ/専用ランタイム）が必要
2. **「1アプリに全部詰める」と機能過多で破綻する**
   - wheelsUp は機能を足すたびに「分かりにくい」FBを受けた
   - 接客版は **「1業界・1チェックリスト・1お手本」のシンプル構成で別アプリ**として切るべき
3. **採点はバックグラウンド処理（キュー/Cron）にすべき**
   - 同期処理は規模が増えると必ずタイムアウトする
4. **「印象でなく観察可能な行動」で採点する設計が肝**
   - 「良い接客だった」ではなく「必須ワードを言った/言わない」で採点 → 客観性・標準化を担保

## 6. 推奨アクション

| 優先 | アクション | 狙い |
|---|---|---|
| 1 | フェーズ1（接客採点PoC）を**別アプリ**として設計 | 既存資産で最短に市場の追い風を捉える |
| 2 | 接客チェックリストを現場と共同定義 | 「正解がある研修」の正解を固める |
| 3 | トップ販売員の接客をお手本データ化 | 採点基準の現場実証 |
| 4 | フェーズ2（ロープレ）の技術設計・コスト試算 | 投資判断の材料 |

**結論：今は「作る」より「どこに張るか」を決めるフェーズ。フェーズ1から小さく実証するのが最も勝率が高い。**
